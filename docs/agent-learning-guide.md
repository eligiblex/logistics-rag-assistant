# 物流异常处理 Agent 学习指南

这份文档按“先跑通、再断点、最后能讲”的顺序学习。项目中的订单、轨迹和工单均为本地演示数据，不连接真实物流系统。

## 1. 先理解它为什么算 Agent

普通 RAG 只有“检索 → 生成”。本项目的 Agent 会根据任务状态选择工具、保存工具结果、在敏感动作前暂停，并在人工决定后从 SQLite 恢复执行：

```text
接收请求 → 制定计划 → 调用知识检索/运单查询/异常评估
                              ↓
                    是否涉及工单或理赔？
                      ↙ 否              ↘ 是
                 生成答复          暂停并等待审批
                                         ↓
                                批准/拒绝后恢复 → 生成答复
```

它没有把工作流藏在框架里，而是用显式状态机实现。优点是容易调试、可测试、可解释；缺点是路由规则需要维护，复杂场景可再替换为模型结构化决策或 LangGraph。

## 2. 按顺序打断点

1. `src/web_api.py` 的 `start_agent`：观察 HTTP 输入怎样进入业务层。
2. `src/agent/service.py` 的 `start`：观察一次运行从 received 开始。
3. `_plan`：看意图、运单号和工具计划怎样产生。
4. `_execute`：看 RAG、运单查询和异常评估的输出怎样写回状态。
5. `_needs_approval`：看敏感动作怎样被拦截。
6. `decide`：批准后执行的是本地演示工单，拒绝时不会调用动作工具。
7. `_finalize`：模型只拿已记录的工具结果生成答复。
8. `src/agent/store.py` 的 `save/get`：理解中断恢复为什么不会丢状态。

## 3. 用 Swagger 完整演示

启动 `python main.py` 后打开 `http://127.0.0.1:8000/docs`。

先调用 `POST /api/agent/runs`：

```json
{
  "query": "请为 YT87654321 创建工单处理延误"
}
```

返回的 `status` 应为 `waiting_approval`。复制 `run_id`，再调用：

```text
POST /api/agent/runs/{run_id}/decision
```

请求体：

```json
{"approved": true}
```

最终状态是 `completed`，`tool_results` 中会出现 `create_demo_escalation`，并明确标记 `local_demo`。

可直接测试的演示运单：

| 运单号 | 场景 |
| --- | --- |
| SF12345678 | 正常运输，低风险 |
| YT87654321 | 天气延误，中风险 |
| JD11223344 | 包装破损，高风险 |

## 4. 面试表达（不要背代码）

可以按下面四句话讲：

1. 我先把物流问答从单一 RAG 升级为显式状态机 Agent，把检索、运单查询、异常评估和动作执行拆成白名单工具。
2. 每个工具的输入输出都会写入运行状态和 Trace，便于定位“规划错、工具错还是生成错”。
3. 工单、投诉、理赔等动作经过人工审批门，Agent 会把状态保存到 SQLite，服务重启后仍能按 run_id 恢复。
4. 外部物流接口尚未接入，所以项目使用演示订单和本地工单，并在返回中明确标注，避免把模拟能力说成真实生产能力。

## 5. 高频追问

**为什么不直接让模型随意调用工具？** 物流动作有副作用，先做工具白名单和人工审批更安全；模型适合生成和辅助决策，权限边界由程序控制。

**SQLite 有什么限制？** 适合单机演示和学习。多实例生产环境应使用 PostgreSQL 等共享存储，并增加乐观锁、幂等键和任务队列。

**怎样防止重复建单？** 当前演示只允许 waiting_approval 状态决策一次；生产还要把 run_id 作为幂等键交给真实工单接口。

**下一步怎么升级？** 用模型结构化输出替换关键词路由；增加工具超时与重试；接入真实但脱敏的订单沙箱；建立包含工具选择、任务完成率和拒答率的评测集。
